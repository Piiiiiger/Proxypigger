A proxy panel is a high-value target. A few layers of hardening go a long way.

## Panel hardening

- Strong, unique credentials and **two-factor auth** (TOTP).
- A non-default panel port and a long, random web base path.
- TLS on the panel (directly or via a [reverse proxy](/docs/operations/reverse-proxy)).
- The built-in **login limiter** blocks an IP/username after 5 failed attempts
  in 5 minutes (for 15 minutes), and the panel can route its own egress through
  an outbound.

See [First login](/docs/guide/first-login) for the full checklist.

## IP limits

Set an **IP limit** per client (see [Clients](/docs/config/clients)) to cap how
many networks the client can be online from at once, counted across every server
the panel manages: an IPv4 /24 is one network, and so is an IPv6 /64. Mobile
carriers send one phone out through several addresses of a pool at once, so
single IPv4 addresses would count one phone several times. When the range holds
one of the panel's servers or an allowlisted address, the address alone is the
network instead, so a ban never cuts off a relay.

The panel enforces the limit itself; it needs no Fail2ban and no firewall rules.

- When a client goes over its limit, the networks it used least recently are
  banned for that client for the ban duration (**IP limit ban** in the panel
  settings, default **30 minutes**). A ban is a routing rule in the Xray config of
  every server that serves the client, applied without restarting Xray; other
  users behind the same address are not affected.
- The panel's own servers (each node's address and the address its agent
  connects from, so relays are covered), the **IP limit allowlist** and private
  ranges are never counted or banned.
- The admin panel and the client's own portal both show the slots in use (e.g.
  `2/3`), the IPs online right now with their servers, and running bans with the
  time left; the admin can lift a ban. Relay addresses never appear there. Every
  ban and unban is also logged to `/var/log/x-ui/3xipl-banned.log` (`x-ui banlog`).

Connections already open when a ban starts run until they close; new connections
from the banned network are refused.

## Abuse prevention

The panel can watch for accounts that abuse the servers: spam, BitTorrent, port
scans, attacks, crawling, repeated speed tests, hours at full speed and bulk
sign-ups on AI, Google and Microsoft. It looks at
connections and traffic only, never at their content, so ordinary use such as
downloading software never counts. Nor do connections that stay within the
panel's servers: a banned device's retries into its blackhole, and a relay's hops
on to the next server, which checks the real destinations itself.

- **Per server, off by default.** On the **Abuse** page (防滥用) each server, the
  panel's own core and every agent node, is **off**, **observe** or **enforce**.
  Observe records hits and tells the admins; enforce does what each rule is set
  to do. Observe for about a week first and tune the thresholds on what it
  records. The page marks a server whose agent does not report the current
  `abuse-v5` capability as needing an update.
- **Rules.** On an enforcing server each rule is set to **record** (tell the
  admins), **warn** (also tell the user, at no cost) or **ban**. Full speed warns
  after 2 hours and, while the rule bans, strikes after 4.
- **Suspect hits.** A hit worth a look but too weak to count is *suspect*: the
  admins see it on the page and in the 09:00 digest, and it never bans, warns or
  costs a strike, whatever the rule is set to do. Spam, BitTorrent, port scans,
  attacks and crawling (its sites) are suspect from half their limit. A rule
  reports an account as suspect at most once an hour, and not within the hour
  after it struck.
- **Port scans.** Only connections to bare IP addresses count. A scan strikes on
  login or database ports across many addresses, on many ports of one address, or
  on many addresses each probed once or twice over TCP within five minutes. Many
  addresses reached over UDP or again and again, as peer-to-peer and chat apps do,
  are only suspect, and so are 32 or more addresses in one IPv4 /24.
- **Strikes and locks.** A strike bans the account on every server for 30
  minutes. The fourth strike within 30 days locks it until an admin lifts the
  lock, which also clears its strikes. IP-limit bans share the history but never
  count as strikes.
- **Bulk sign-ups on AI, Google and Microsoft.** Each platform's own sign-in or
  sign-up server is watched: `auth.openai.com` (ChatGPT), `accounts.google.com`
  (Google, Gemini included) and `signup.live.com` (Microsoft). The rule counts the
  minutes of an hour, and of a day, in which an account connected to one of them:
  a person signs in for a minute or two, while bulk sign-ups keep at it. OpenAI and
  Microsoft count once over their limit. Google's server also gets browsers' and
  phones' background checks, so one hour over its limit is only *suspect* (listed
  for the admins, never a strike or a warning); it counts when the limit breaks in
  several hours of a day (default 3) or by half again in one hour. An SMS-code,
  temp-mail or captcha-solving site the same day halves any platform's hourly limit
  and is named in the hit; anti-detect browsers are not counted, as ordinary users
  run them. Each hit also shows the account's traffic in that hour. The rule cannot
  tell a login from a sign-up or count the accounts made, and it only records until
  you change its action, even on enforcing servers.
- **Sign-ups.** The user page counts sign-ups per network (an IPv4 /24 or an IPv6
  /48) over 24 hours. A network reaching the limit (default 3) is reported to the
  admins with the accounts it made; while the guard bans, it cannot sign up again
  until the day is over.
- **Notices.** Bans, locks and warnings reach the user's bound Telegram and the
  admins. Hits that only record reach the admins at once for scans and attacks,
  and otherwise in a digest at 09:00 (UTC+8); suspect hits always wait for the
  digest.
- **What users see.** The user page opens with the usage rules, the warning to
  turn off location services on phones first; it can be closed or hidden for 7
  days. The page and the bot list each account's bans of the last 90 days, with
  when and why.

Bans are routing rules, like the IP limit's: connections already open finish,
new ones are refused. An admin lifts a ban or clears strikes on the Abuse page,
in the user dialog or on the bot's user card.

## Network tuning (BBR)

The `x-ui` menu (**25 — Enable BBR**) toggles Google's BBR congestion control
(`net.ipv4.tcp_congestion_control = bbr`, `net.core.default_qdisc = fq`), which
often improves throughput on congested links.

## Keep current

Update 3x-ui and Xray-core regularly — security fixes land in new releases. Watch
the [releases page](https://github.com/MHSanaei/3x-ui/releases) and see
[Update & uninstall](/docs/guide/update-uninstall).
